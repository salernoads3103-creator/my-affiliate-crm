# CRMONIA — короткий список технічного боргу

**Перевірено:** репозиторій `develop`, 2026-10-24. Це статичний огляд коду,
SQL і документації; стан remote-середовищ окремо не перевірявся. Пріоритети
нижче відображають послідовність зниження ризику, а не підтверджені інциденти.
У цьому огляді не встановлено конкретної активної P0-вразливості або втрати
даних; P0 нижче — блокери активації окремих можливостей.

## P0 — блокери перед активацією конкретних можливостей

1. **TikTok Pixel зміни ще не активовані.** Поточне робоче дерево має
   незакомічені зміни, які читають `workspace_landings.tiktok_pixel_id` і
   розширюють `get_workspace_landings`; міграція
   `supabase/migrations/20261024140000_landing_tiktok_pixel_configuration.sql`
   не була застосована. Ризик — несумісність коду із БД при ранньому розгортанні.
   Спершу перевірити повний ланцюжок міграцій і RLS-тест на disposable БД, потім
   окремо спланувати розгортання міграції й сервера. Це відомий rollout-ризик,
   а не доказ пошкодження даних.
2. **Післяплата Нової пошти заблокована.**
   `docs/nova-poshta-mvp.md`, `src/lib/shipping/nova-poshta.server.ts` і
   `tests/shipping.test.ts` фіксують, що точні контракти NovaPay та «Контролю
   оплат» для API v2.0 не підтверджені. Не використовувати цей потік для
   післяплати до перевірки офіційного контракту та окремого тестування.

## P1 — архітектура, доступ і масштабування

1. **Два API можуть розійтися.** TanStack Start містить workspace API та є
   основним шляхом; `server/src/` реалізує переважно CRUD лідів. Кореневий
   `README.md` і `server/README.md` все ще описують backend-и як
   взаємозамінні, хоча їх покриття різне. Рішення: не додавати нові endpoint-и
   паралельно; спочатку звірити використання `VITE_API_URL`, потім або лишити
   Express лише сумісним lead API, або окремим рішенням поступово вивести його
   з використання. Якщо потрібна повна окрема інсталяція — визначити спільний
   контракт і contract-тести до розширення.
2. **Немає автоматичного CI для безпеки та міграцій.** SQL-сценарії є в
   `supabase/tests/`, але `.github/workflows/` відсутній. Центральна міграція
   workspace-доступу велика (`supabase/migrations/20261022090000_workspace_access_foundation.sql`).
   Ризик — зміни permissions, RLS, `SECURITY DEFINER` і збереження даних можуть
   пройти без автоматичного regression check. Додати PR workflow з окремим
   disposable Supabase/PostgreSQL job; remote secrets та production DB не
   використовувати.
3. **Постачальник ще не є окремою сутністю.** `products.supplier_name` — текст,
   а `workspace_nova_poshta_settings` зберігає один набір параметрів на
   workspace. Це відповідає поточному MVP, але не забезпечує заявлену модель
   кількох постачальників із власними операторами й відправниками. До їх
   підключення визначити owner/scope, правила доступу й зв’язки; мігрувати
   поступово з preservation-тестами.
4. **Списки лідів читають необмежений набір.**
   `src/lib/leads/service.ts` та `server/src/services/lead.service.ts` роблять
   `select("*")` без серверної пагінації; `stats()` завантажує всі доступні
   ліди й рахує 14-денний рядок у пам’яті. Ризик — повільні відповіді й зайве
   споживання пам’яті зі зростанням даних. Додати обмежену серверну пагінацію,
   мінімальні поля й агрегатну статистику з перевіреною RLS-областю.
5. **Замовлення поки однопозиційне.**
   `workspace_orders` зберігає один товар/офер на замовлення; немає окремої
   таблиці order items. Для сценаріїв із комплектами/допродажами потрібні
   позиції зі snapshot-даними. Не змінювати схему до підтвердження сценарію;
   перед багатотоварним UX спроєктувати append-only перехід і preservation старих
   замовлень.

## P2 — документація, типи й інженерний процес

1. **README-інструкції відстають від коду.** `README.md` і `server/README.md`
   містять назву Lumen, стару схему `leads`, твердження про production-grade
   якість та взаємозамінність API. Це дезорієнтує нових інженерів. Оновлювати
   їх окремою документаційною зміною після узгодження локального запуску й
   deployment-процесу.
2. **Перевірки не налаштовані як PR gate.** У кореневому `package.json` є lint,
   build і test, але немає workflow; `server/package.json` не має власного
   тестового набору, а lint-команда лише повідомляє, що лінтер не налаштовано.
   Аудит 2026-10-23 зафіксував значний Prettier/CRLF-борг. Спершу зафіксувати
   базовий стан і перевіряти змінені файли; не запускати масове форматування як
   частину функціонального завдання.
3. **Supabase типи та схема потребують відтворюваного процесу.** Типи лежать у
   `src/integrations/supabase/types.ts`, а доступні міграції розвивають схему
   окремими кроками. У кореневому `package.json` не видно команди генерації
   типів. Документувати версію локальної схеми, команду генерації та перевірку
   diff, не редагувати застосовані міграції.
4. **Адміністративна сторінка велика, але UI ще змінюється.**
   `src/routes/_authenticated/administration.tsx` має близько 1,850 рядків.
   Це підвищує вартість пошуку логіки, але не виправдовує загальний UI-рефакторинг
   під час MVP. Виносити стабільні правила, запити та валідацію тільки в межах
   конкретних змін; UI-компоненти розділяти за реальною повторюваністю.

## Не є поточними реалізаціями

Реєстр доменів і автоматична публікація, постачальники та їхні оператори,
окремі налаштування НП на постачальника, bidirectional інтеграції кол-центрів,
керування рекламними кампаніями й автоматизація рутини — напрям або прогалина
відносно roadmap, а не наявний функціонал. Render зараз є development-хостингом;
план перенесення на VPS/іншу платформу ще потребує вимог до backup, оновлень і
відновлення.
