# CRMONIA — аудит стандартів розробки та якості коду

**Дата:** 2026-10-23 · **Гілка:** `develop`
**Обсяг:** статичний огляд структури, API, авторизації, SQL-міграцій, адміністративного інтерфейсу, типізації, залежностей і наявних перевірок.

## Підсумкова оцінка

У CRMONIA вже є корисна основа: строгий TypeScript у застосунку й Express-сервері, серверні перевірки доступу, PostgreSQL RLS, функції дозволів, журналювання змін доступу та SQL-сценарії для перевірки доступу й збереження лідів. Це добрі будівельні блоки для комерційного продукту.

Підтримуваність поки нижча за ціль незалежної команди. Основні причини — два частково паралельні API для лідів, великий адміністративний маршрут, ручні приведення типів, необмежене читання даних, відсутність автоматизованих тестів застосунку та CI, а також значний борг форматування. Поточна успішна збірка підтверджує лише проходження збірки в наявному середовищі; вона не підтверджує безпеку, коректність RLS, збереження даних у production чи готовність до розгортання.

Під час цього аудиту код бізнес-логіки не переписувався, функціональність CRM не змінювалася, SQL до Supabase не застосовувався, секрети не читалися й не змінювалися. Оновлено лише `AGENTS.md` і цей звіт.

## Сильні сторони та наявний захист

- Міграція `supabase/migrations/20261022090000_workspace_access_foundation.sql` вмикає RLS для таблиць робочих просторів і лідів, додає політики за межами доступу та явно видає/відкликає права для функцій. Функції дозволів і журналювання визначені в SQL, зокрема `has_workspace_permission` і `audit_workspace_access_change`.
- Серверні API перевіряють bearer-токен і передають автентифікований контекст до Supabase. Адміністративні маршрути викликають спільний контекст доступу та/або перевірку дозволу; база даних залишається другим рівнем контролю через RLS.
- Токен запрошення зберігається як хеш у схемі. Сценарії `supabase/tests/workspace-access.sql`, `prepare-lead-preservation.sql` і `assert-lead-preservation.sql` свідчать, що доступ і збереження даних вже враховувалися під час розробки.
- TypeScript налаштований у strict-режимі як для основного застосунку, так і для окремого сервера.

Ці переваги не замінюють автоматичне виконання тестів на кожному Pull Request. SQL-сценарії цього аудиту не запускалися, а віддалена база не використовувалася.

## Технічний борг за зонами

- **API і межі модулів:** дубльовані lead-схеми/сервіси, два HTTP-клієнти з різною маршрутизацією, неповний паритет між TanStack і Express, відсутність автоматизованої перевірки API-контракту.
- **Доступ і база даних:** RLS/RBAC вже мають хорошу основу, але SQL-перевірки ручні; великий migration-файл складний для огляду; немає відомого CI для регресій політик.
- **Типізація:** основна компіляція не охоплює Express; типи workspace-таблиць і runtime-перевірка API-відповідей неповні; ручні приведення до `Lead` маскують можливий дрейф схеми.
- **Масштабування:** lead-списки не мають пагінації, а статистика читає повний список і обчислюється на Node стороні.
- **Адміністративний UI:** маршрут на 1754 рядки поєднує кілька різних відповідальностей.
- **Якість і доставка:** немає test scripts/CI; форматування блокує ESLint і Prettier; серверний lint не виконує перевірки.
- **Продуктові інтеграції:** attribution, публічний ingestion, зовнішні call-center контракти й інтеграція Нової пошти поки не описані у виконуваних API/схемах.
- **Документація:** старий бренд і завищені твердження про готовність не відповідають поточним постійним правилам і покриттю backend-ів.

## Поетапний план покращень

### P0 — безпека та ризики втрати даних

1. До розширення production-трафіку зафіксувати allowlist origin для Express і заборонити старт production із порожнім списком.
2. Припинити повертати сирі помилки БД/провайдера; залишити внутрішній лог із correlation ID та стабільну публічну схему помилок.
3. Під’єднати на Pull Request локальні негативні RBAC/RLS сценарії: анонімний доступ, чужий workspace, заборонене делегування, operator/team/offer scope, відкликання прав.
4. Додати тест збереження існуючих лідів до/після міграції на disposable БД і задокументувати вимоги до backup/restore перед реальним застосуванням SQL.

Під час статичного огляду не знайдено підтвердженої критичної P0-вразливості чи виконаного видалення даних. Ці кроки є воротами для подальшого розширення, а не твердженням про вже підтверджений інцидент.

### P1 — архітектура та складність підтримки

1. Вирішити, чи Express має бути реальною повною альтернативою TanStack. До рішення не додавати в нього нові endpoint-и без контрактів.
2. Увести пагінацію й межі запитів для лідів; перенести статистичні агрегації в БД/RPC із перевіреним workspace scope.
3. Закріпити межі між мінливим UI та бізнес-логікою: у наступних змінах переносити доменні правила, дозволи, валідацію і роботу з API в типізовані модулі, які UI викликає через явні контракти. Не планувати масштабну перебудову екранів до стабілізації сценаріїв MVP.
4. Узгодити версії TypeScript/Supabase, додати окрему перевірку сервера й lockfile-стратегію для двох пакетів.

### P2 — читабельність, документація та стандарти

1. Узгодити правила line ending, ESLint та Prettier, виправити форматування контрольованою окремою зміною.
2. Описати єдиний API-контракт із запитами, відповідями, auth, помилками, pagination і версіонуванням.
3. Синхронізувати README з назвою CRMONIA, фактичними backend-ами та реальними рівнями готовності.
4. Вирівняти `Database` типи з локальною схемою й прибрати неперевірені casts поступово, з тестами на межах.

### P3 — косметичні покращення

1. Після стабілізації ключових сценаріїв оцінити, які частини адміністративного UI варто виділити; до цього витягати лише компоненти з явним повторним використанням або користю для конкретної зміни.
2. Прибрати застарілі/непотрібні ESLint disable-коментарі та окремо оцінити React Refresh/exhaustive-deps попередження.
3. Після узгодження API інтеграцій описати приклади для HTML-лендів, call-center webhook-ів і provider adapter Нової пошти.

## Яких автоматизованих тестів бракує

У кореневому `package.json` немає test script; у workflow-ах GitHub Actions перевірок не знайдено. Є SQL-сценарії для workspace access і збереження лідів, але вони не виконувалися в цьому аудиті й не запускаються автоматично.

Рекомендована піраміда тестів:

- **Unit:** Zod-схеми/нормалізація API-входів, мапінг помилок, permission-scope рішення, pagination/статистичні агрегації, формування audit payload.
- **API integration:** кожен адміністративний маршрут з bearer-token матрицею ролей і негативними перевірками; валідація відповідей та однакові статуси помилок.
- **DB/RLS integration:** міграції на disposable Supabase/PostgreSQL, перевірки `SECURITY DEFINER` grants, RLS для різних workspace/team/operator/offer, заборона підвищення привілеїв і збереження даних.
- **End-to-end:** вхід, створення/прийняття/відкликання запрошення, зміна ролі/індивідуального дозволу, CRUD ліда та перевірка області видимості після відкликання доступу.
- **Contract:** якщо обидва backend-и залишаються, один набір контрактних сценаріїв для TanStack та Express; для зовнішніх інтеграцій — idempotency, підпис webhook-а, повтори й конфлікт статусів.

## Рекомендований GitHub Actions CI для Pull Request

Workflow має працювати на Linux runner без production secrets і без підключення до віддаленого Supabase:

1. Встановити підтримувану версію Bun і виконати `bun install --frozen-lockfile`.
2. Виконати Prettier check, ESLint і `bun x tsc --noEmit` для кореневого застосунку.
3. Для `server/` встановити залежності за зафіксованим lockfile, виконати справжній ESLint, TypeScript build і тести.
4. Виконати `bun run build`.
5. В окремому job запустити локальну disposable Supabase/PostgreSQL, застосувати migrations лише до неї та запустити SQL/RLS/preservation тести.
6. Кешувати пакети за lockfile; зробити ці перевірки обов’язковими до merge. Застосування remote міграцій і використання production secrets у PR CI не потрібні.

Через поточні 105 файлів, що не проходять Prettier, форматування варто спершу виправити окремим контрольованим PR, а потім зробити Prettier check блокувальним.

### Обмеження висновків

Це статичний аудит репозиторію на `develop`. Не проводився live security review, навантажувальний тест, перевірка розгорнутого середовища чи запуск SQL на локальній/віддаленій базі. Успішні build і TypeScript check не доводять відповідність privacy/security вимогам або production readiness. Перед рішенням про production потрібні автоматизовані тести, перевірка конфігурації середовища, міграцій і процедур відновлення даних.
