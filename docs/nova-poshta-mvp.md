# Інтеграція Нової пошти: API v2.0

Поточний серверний адаптер використовує офіційний український JSON endpoint https://api.novaposhta.ua/v2.0/json/ без окремої авторизації через JWT. Кожен запит — POST із apiKey, modelName, calledMethod та methodProperties. Ключ розшифровується лише на сервері й ніколи не повертається браузеру чи логам.

Довідники запитуються через методи v2.0 для міст (Address.getCities), відділень і поштоматів (Address.getWarehouses), профілів відправника (Counterparty.getCounterparties) та пов'язаних адрес і контактів (Counterparty.getCounterpartyAddresses, Counterparty.getCounterpartyContactPersons). У БД зберігаються UUID Ref із відповіді довідника; текстова назва не використовується замість Ref. Перед спробою створити ТТН сервер повторно перевіряє вибрані refs.

Звичайне внутрішнє відправлення створюється через InternetDocument.save. Перед передаванням операції в робочий акаунт необхідна окрема перевірка наданого Новою поштою доступу та сумісності реквізитів відправника й отримувача. У цьому завданні реальних запитів до API не було; adapter tests використовують тільки mock fetch.

## Післяплата

У БД зберігаються сума післяплати в копійках і вибраний режим: novapay або payment_control. Це різні фінансові послуги, а не взаємозамінні назви одного параметра.

- Для NovaPay офіційна сторінка описує окремий договір післяплати та зарахування коштів на рахунок. Точний v2.0 API-контракт для підключення цієї послуги не вдалося звірити: developer portal у середовищі перевірки повертає 403.
- Контроль оплат також не вважається еквівалентом договору NovaPay. Точну схему та умови доступу для цього режиму не підтверджено.
- ТТН з будь-яким режимом післяплати серверно заблокована до підтвердження конкретного контракту та параметрів. Адаптер не відправляє AfterpaymentOnGoodsCost або BackwardDeliveryData навмання.

Після отримання доступної офіційної специфікації окремо перевірити поля, вимоги до договору та відповіді для кожного режиму. Лише після цього можна відкрити відповідний маршрут у коді й додати fixtures з підтвердженим payload.

## Захист і активація

Для налаштувань і створення ТТН потрібен дозвіл shipping.manage, а також orders.manage у scope відповідного ліда. Таблиці не дозволяють браузеру записувати дані доставки або читати зашифрований ключ. Сервер перед створенням атомарно закріплює одну спробу через claim_workspace_order_waybill. Повторний claim не запускає другу відправку. Якщо результат зовнішнього запиту неоднозначний, стан unknown блокує автоматичну повторну спробу.

Нова append-only міграція supabase/migrations/20261024120000_nova_poshta_delivery_mvp.sql залишається незастосованою. Спершу перевірити її та supabase/tests/nova-poshta-shipping-rls.sql на disposable/local Supabase; до віддаленої Supabase в цьому завданні SQL не застосовувався. Необхідний серверний секрет: NOVA_POSHTA_CREDENTIALS_ENCRYPTION_KEY — Base64-кодування 32 випадкових байтів. API key облікового запису Нової пошти зберігається в зашифрованому вигляді в БД.
