# Workspace Access API

Workspace APIs use the existing Supabase Auth bearer session. The server validates the token with Supabase Auth; database operations run with that user's JWT and are still protected by workspace permissions and RLS. The browser cannot write workspace membership, ownership, or permission rows directly.

## List the caller's workspaces

`GET /api/workspaces`

Returns `{ "success": true, "data": WorkspaceSummary[] }`. Ordinary users receive only active memberships returned by `my_workspaces()`. A system Super Admin can see all workspaces. The frontend may remember the selected ID in local storage, but it resolves that ID only against this server-returned list; it is not an authorization input.

## Create the account owner's workspace

`POST /api/workspaces`

Requires an authenticated account with a confirmed email. The initial self-service flow permits one workspace created by an account; retries return the existing workspace ID and do not create another workspace.

Request:

```json
{ "name": "My e-commerce business" }
```

`name` is trimmed and must contain 2–100 characters. The server ignores client-supplied workspace IDs, ownership, membership, and roles. On success, returns HTTP 201 with `{ "success": true, "data": { "id": "<WORKSPACE_UUID>" } }`.

The creator becomes an active workspace Admin and receives current workspace-scoped permissions except `permissions.manage`. They are not added to `main` and do not become a system Super Admin. The workspace slug and all identifiers are generated by the database. Direct browser writes remain revoked; the authenticated-only `create_workspace_for_current_user(text)` security-definer RPC is the only creation path and is idempotent per account.

Common errors use the standard API envelope: `401 UNAUTHORIZED` for a missing/invalid session, `400 VALIDATION_ERROR` for an invalid name, `403` for an unconfirmed account or denied operation, and `500 INTERNAL_ERROR` for an unconfirmed database result.

## Accept a workspace invitation

The invitation flow remains separate from self-service workspace creation:

- `POST /api/workspaces/{workspaceId}/invitations` requires `members.invite`; assigning the Admin role also requires `members.assign_admin`.
- `POST /api/invitations/validate` validates a hashed, expiring token and returns the invitation email, role, and workspace name.
- `POST /api/invitations/accept` requires a confirmed authenticated account whose email exactly matches the invitation. It adds membership only to the invited workspace.

Invitation tokens are not stored in plaintext in the database. Normal registration without an invitation creates an account only; after email confirmation the user creates their own isolated workspace. A user who accepts an invitation to `main` receives only the rights that invitation grants, so do not invite an independent buyer to `main` when they should have a separate account-owned workspace.

## Workspace switching

The authenticated UI shows a selector only when the server returns multiple workspaces. Changing selection clears cached queries and uses the selected workspace ID in existing module requests. Every API and RLS policy still re-checks access; local storage is only a UI preference. Invitation acceptance selects the workspace that was actually returned by the acceptance API.

Lead endpoints preserve their existing `/api/leads` paths and accept an optional `workspaceId` query parameter. The CRM sends the selected workspace for list, search, statistics, create, update, and delete operations. The lead service uses that value only as a query scope and sets `workspace_id` on new records; the authenticated Supabase client and existing RLS policies remain the final authorization boundary. Calls from older clients without the parameter keep their previous RLS-filtered behavior.

## Current limitations

- The account may create one self-owned workspace; joining more workspaces is through invitations.
- The standalone legacy Express service is not used by the Render Blueprint for the TanStack application. Keep `VITE_API_URL` unset for this deployment; the legacy Express lead API has not been extended with active-workspace selection.
- The creator can invite users and assign supported workspace roles, but cannot manage individual permission overrides (`permissions.manage` is intentionally withheld). Fine-grained delegation for independently owned workspaces needs a separate security design.
- Password recovery is not implemented in the current auth UI; it does not block first registration but needs a separate user-facing flow before broader onboarding.
